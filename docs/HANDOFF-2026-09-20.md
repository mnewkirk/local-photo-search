## Reaching the machines (read this first)

- From the Mac, the Claude app **cannot reach LAN addresses** ("No route to
  host" on a same-subnet IP — the macOS Local Network permission symptom). Use
  the **Tailscale** addresses instead:
  `TS=/Applications/Tailscale.app/Contents/MacOS/Tailscale; $TS ip -4 <nas-host>`.
- NAS web API `:8000`, desktop replica `:8001`, LM Studio on the desktop `:1234`.
- SSH to the NAS: **one attempt per command, never a retry loop** (UGOS
  auto-blocks the client IP). Always `ssh -n …` or feed a script with
  `ssh … 'bash -s' <<'EOS'`. Inside such a script, every `docker compose run` /
  `docker exec` needs `< /dev/null` or it **eats the rest of the script** from
  stdin. In zsh never name a loop variable `path` (it is `$PATH`).
- Read-only SQL on the live DB:
  `docker exec photosearch python -c "… sqlite3.connect('file:/data/photo_index.db?mode=ro', uri=True) …"`.
- Deploy = NAS first, then replica: `POST /api/admin/git-pull` → `docker-build`
  (SSE; NAS only) → `restart`, then poll `/api/admin/version` for the SHA. The
  worker fleet survives both restarts (it rode through ~10 yesterday).

## Things that bit yesterday (so they don't bite again)

- High load average with idle containers = threads in uninterruptible I/O wait.
  `vmstat 1` (`b`, `wa`) confirms; `ss -tni` on port 445 names an SMB client
  doing a bulk read. A desktop backup reading the share at ~50 MB/s slowed
  ingest to one file per 3 minutes.
- `count_unprocessed == 0` is not "done" (exhausted attempts; text passes before
  describe exists). `batch_state` exists because of this.
- A dry run is only a dry run if it opens the DB `mode=ro` and never hashes.
- Every review of subagent work found a real defect, and the live dry runs found
  two more that reviews missed (a root guard too strict for an env-configured
  `PHOTO_ROOT`; thresholds tuned on 2.4% coverage that bit at 98.9%). Look at
  the actual photos before trusting a tag statistic.
